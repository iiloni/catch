# 0017: A changelog derived from tags and commits

Status: accepted (2026-10-03)

## Context

GitHub Releases listed build artifacts but not what changed, and a documentation site will
later need the same change list per version. Releases are tags only (ADR 0009): versions
are chosen explicitly, nothing commits a version bump, and a stable release can promote an
earlier preview's exact commit.

## Decisions

- **No committed `CHANGELOG.md`.** A changelog commit would land after the tag it describes
  and need its own pull request through protected main, and a promotion would make the
  file's order disagree with history. The changelog is computed from tags and history each
  time it is needed.
- **Commits are the source, not pull requests.** Direct commits to main are part of a
  release, which rules out GitHub's generated notes on their own. A squash merge's `(#N)`
  suffix supplies the pull request link; other commits link to themselves. Merge commits
  are left out, since the commits they bring in carry the meaningful subjects.
- **The range follows the channel.** A preview counts from the highest lower tag of either
  channel reachable from it; a stable release counts from the highest lower stable tag, so
  it folds in the previews it supersedes, including when it promotes an older preview's
  commit. "Highest reachable tag" is the rule the version bump already uses, and both share
  `releaseTags` in `scripts/release.ts`.
- **One generator, in TypeScript** (`scripts/changelog.ts`), with Markdown for a release
  body and JSON for every release. git-cliff was considered for parsing and rendering.
  It would still need the range computed here, a template for the Markdown, and custom code
  for the protocol line and the JSON document, while adding a binary to pin and verify in
  the release job that holds write permissions. The Conventional Commit grammar needed is
  one expression plus a footer, so the parser is smaller than the integration, and the
  release tooling stays dependency-free, unit-tested TypeScript. release-please and
  Changesets assume version-bump commits and release pull requests, which ADR 0009 rejects.
- **The protocol is compared across the range.** The notes state the old and new
  `API_PROTOCOL_VERSION` and supported range when they differ (ADR 0013), with the upgrade
  order those numbers imply. They are read from the source text of `protocol.ts` at each
  tag rather than by running tagged code; an unreadable file is an error rather than a
  silently missing line, and a unit test checks the current file.
- **The JSON output is a contract.** It carries a `schemaVersion`, every release newest
  first and the unreleased commits, with each entry in exactly one section. The site
  renders it at build time; its text is unescaped commit text.
- **Notes are generated twice in a release.** The version job writes them to the run
  summary before any build, so a generation failure costs no signed artifact; the
  publishing job writes the release body. Both run the tagged commit's own generator, as
  the rest of `release.yml` does.
- **One value locates the changelog.** `CHANGELOG_BASE_URL` in `scripts/changelog.ts` is
  null until the site exists, and release bodies link to GitHub's compare view for the
  range. Once set, they link to `<base>/<version>`.

## Consequences

- Commit subjects and `BREAKING CHANGE:` footers are published text. A poor subject can
  only be corrected by editing the GitHub Release afterwards.
- Notes for a tag are reproducible from a full clone, so older releases can be backfilled
  or re-rendered when the format changes, but a tag's notes are generated by the code at
  that tag during its release.
- The release jobs fetch full history. A shallow clone is rejected instead of producing a
  truncated range.
- A branch merged without squashing lists each of its commits.
